# 说明书 AI 翻译工作流 V1 PRD

**版本：V1.0**  
**目标交付时间：2026 年 8 月底**  
**产品阶段：本地可运行 MVP / 内部验证版**

---

## 1. 项目背景

目前产品说明书中英文翻译主要由产品经理人工完成。

公司已有约 9 份不同产品、不同版本的中英文说明书，可作为历史翻译语料，但目前尚未形成统一、结构化、可复用的语言资产，例如：

- 术语库
- 中英文翻译记忆
- 产品及部件标准命名
- UI / 软件名称禁改规则
- 翻译风格规范
- 翻译 QA 规则

人工翻译过程中可能出现：

- 同一术语在同一说明书不同章节翻译不同；
- 不同产品对相同部件使用不同英文名称；
- 产品名称、部件名称、UI 名称被误改；
- 历史说明书之间存在不同译法；
- 重复内容仍需要重新翻译；
- 图片、表格、页眉页脚中的中文容易遗漏；
- 翻译完成后仍需大量人工检查和排版。

因此，希望建立一套能够持续沉淀公司语言资产，并约束 AI 按统一标准进行翻译的说明书 AI 翻译工作流。

---

# 2. 产品定位

本项目不是通用聊天式翻译机器人，而是一套：

**基于公司历史语言资产、可约束、可审核、可持续沉淀的说明书 AI 翻译工具。**

产品原则：

> AI 负责生成和分析；  
> 人负责必要的业务判断；  
> 系统负责约束 AI 遵守公司已有标准。

系统应尽可能自动完成工作，仅在无法安全自动决策时要求用户确认。

随着语言资产不断积累，需要人工确认的问题应逐渐减少。

---

# 3. V1 核心目标

月底 V1 优先解决一个实际问题：

> **让产品经理上传一份中文 Word 说明书，在少量人工确认后，直接获得一份已经完成英文翻译的 Word 文件。**

同时开始建立可持续复用的公司语言资产。

V1 不追求完整企业级系统，而追求：

- 能真实使用；
- 能处理实际说明书；
- 翻译结果可控；
- 数据可以留下；
- 后续能够继续扩展；
- 不是一次性脚本。

---

# 4. V1 产品形态

V1 采用：

**本地运行的 Web 翻译工作台**

启动程序后，用户通过浏览器访问本地页面，例如：

`localhost:8501`

V1 暂时主要由项目开发者本人使用。

后续可进一步部署至公司内部服务器，使其他产品经理通过浏览器访问。

---

# 5. 目标用户

## 核心用户

负责不同产品说明书维护、翻译和输出的产品经理。

## 潜在用户

市场、销售、研发等有英文技术术语查询需求的人员。

V1 首先服务产品经理的说明书翻译工作。

---

# 6. V1 整体工作流程

```text
上传中文 Word
        ↓
解析文档结构与文字
        ↓
识别术语 / 产品名 / UI名 / 特殊内容
        ↓
查询已有语言资产
        ↓
调用 AI 进行翻译
        ↓
自动执行 QA
        ↓
判断是否存在需要人工确认的问题
        ↓
有问题 → 用户确认
无问题 → 直接继续
        ↓
将译文写回 Word
        ↓
生成英文 Word
        ↓
下载
```

# 7. V1 页面设计

## 7.1 翻译工作台

作为系统首页。

用户可以：

- 选择产品；
- 选择说明书类型；
- 上传 `.docx`；
- 启动翻译；
- 查看处理进度；
- 查看翻译状态；
- 下载最终英文 Word。

示意：

```text
新建翻译任务

产品：
[ DM-Tac G ▼ ]

文档类型：
[ 硬件说明书 ▼ ]

上传文件：
[ DM-Tac_G_CN.docx ]

[ 开始翻译 ]
```

---

# 7.2 待确认页面

系统只展示无法安全自动决定的问题。

例如：

### 历史译法冲突

中文：

感知层

历史译法：

- Sensing Layer
- Perception Layer

AI 推荐：

Sensing Layer

用户可以：

- 采用推荐译法；
- 使用其他历史译法；
- 自定义译法。

---

### 新术语

例如：

微结构光学弹性体

系统显示：

- AI 推荐译法；
- 当前文档出现次数；
- 是否加入术语库。

用户可以：

- 采用并保存；
- 仅当前文档使用；
- 修改译法。

---

### 图片中文

检测到图片可能包含中文时：

- 标记图片所在位置；
- 展示检测到的文字；
- 给出英文建议；
- 提醒用户当前图片仍需要处理。

---

# 7.3 术语库

支持：

- 查看术语；
- 搜索；
- 新增；
- 修改；
- 设置状态；
- 查看适用范围。

V1 术语至少记录：

- 中文术语；
- 英文标准译法；
- 类型；
- 产品 / 适用范围；
- 状态；
- 来源；
- 备注。

状态至少包括：

- Candidate / 候选；
- Approved / 已审核；
- Locked / 锁定；
- Disabled / 禁用。

---

# 7.4 翻译记忆库 TM

记录历史中英文句对。

V1 支持：

- 查看；
- 搜索；
- 保存已确认的中英文译文；
- 翻译时作为 AI 参考。

V1 可以先实现基础匹配。

复杂的模糊匹配与高级 TM 算法放至后续版本。

---

# 7.5 翻译规范

系统保存一份可维护的翻译 Style Guide。

包括但不限于：

- 标题格式；
- 单位格式；
- 大小写；
- 标点；
- Note / Warning 等表达；
- 常见说明书句式；
- 产品文档写作习惯。

V1 可先以 Markdown / JSON 等易维护格式保存。

---

# 8. Word 文档处理

V1 应优先支持实际说明书中最常见的内容：

### 必须支持

- 普通正文；
- 标题；
- 表格中的文字；
- 页眉；
- 页脚；
- 图题 / 表题；
- 基本段落样式；
- 原有图片保留；
- 基本字体、字号、加粗等格式尽量继承。

### V1 尽量支持

- 自动编号；
- 超链接；
- 目录更新；
- 较复杂表格。

### V1 暂不承诺完整支持

- SmartArt；
- 特别复杂的文本框；
- Word 域；
- 高度复杂的交叉引用；
- 特殊插件生成元素；
- 所有第三方 Word 模板特性。

产品目标不是“英文版与中文版每一页像素级完全一致”，而是：

> **最大程度保留原文档结构、样式、图片、表格、编号和页面设置，并自动完成其中可编辑文字的翻译。**

---

# 9. 图片文字处理

V1 不强制实现图片中文字自动替换。

V1 首先实现：

> **图片中文检测 + 提醒 + 英文翻译建议。**

即：

```text
Figure 4 检测到中文：

感知层 → Sensing Layer
相机 → Camera
弹性体 → Elastomer
```

后续版本再支持自动图片本地化。

---

# 10. 语言资产机制

历史说明书中提取出的语言内容默认不得直接视为公司标准。

默认状态：

`Candidate`

系统负责：

- 抽取；
- 去重；
- 聚类；
- 发现冲突；
- 提供历史证据；
- 给出 AI 建议。

经过人工确认后：

`Candidate → Approved`

Approved 资产在后续翻译中优先使用。

Locked 项不得由 AI 自由改写。

---

# 11. AI 翻译规则

AI 翻译不得只依赖一个固定 Prompt 自由生成。

翻译每个文档 / 文本块前，系统需要自动检索：

- 当前相关 Approved 术语；
- Locked 名称；
- 历史 TM；
- Style Guide；
- 当前产品信息。

然后将相关约束一并提供给 AI。

用户无需手工选择术语再提交给 AI。

---

# 12. QA

翻译后系统自动执行基础质量检查。

V1 优先检查：

- 是否存在未翻译中文；
- Approved 术语是否统一；
- Locked 名称是否发生变化；
- 数字是否发生变化；
- 单位是否异常；
- 图号 / 表号是否异常；
- 是否存在明显段落遗漏；
- 同一术语是否出现多个译法。

系统应尽量自动检查，不应将普通 QA 工作全部抛给用户。

# 13. 技术方案

V1 暂定采用：

- Python
- Streamlit
- SQLite
- python-docx
- 可替换 AI Provider

整体结构：

```text
Web UI
   ↓
Workflow
   ├── Word Parser
   ├── Terminology Service
   ├── TM Service
   ├── Translator
   ├── QA
   └── Word Writer
           ↓
       SQLite
           ↓
       AI Provider
```

# 14. 代码结构要求

V1 即使本地运行，也不得写成单文件临时脚本。

建议：

```text
translation_project/
│
├── app.py
│
├── pages/
│
├── services/
│   ├── translator.py
│   ├── terminology.py
│   ├── translation_memory.py
│   ├── qa.py
│   └── ai_provider.py
│
├── document/
│   ├── parser.py
│   └── writer.py
│
├── database/
│   ├── db.py
│   └── schema.py
│
├── prompts/
│
├── assets/
│
├── data/
│
├── outputs/
│
```

目的：

- 后续可维护；
- 不绑定单一 AI；
- 数据与代码分离；
- UI 与核心翻译逻辑分离；
- 方便未来迁移至公司服务器。

# 15. V1 明确不做

月底前以下能力不作为交付要求：

- 公司账号登录；
- 完整权限系统；
- 多人并发；
- 正式公司内网部署；
- React / Vue 等独立前端；
- 企业级数据库；
- 完整审批流；
- 自动修改图片中文字；
- 复杂 TM 模糊匹配；
- 完整术语版本回滚；
- 支持所有 Word 特殊元素。

这些能力不应阻碍 V1 按时交付。

---

# 16. 月底 V1 验收标准

V1 至少需要完成一次完整真实流程：

1. 打开本地 Web 工具；
2. 上传一份实际中文 `.docx` 说明书；
3. 系统成功解析主要文字内容；
4. 能从术语库检索已有术语；
5. 能调用 AI 进行英文翻译；
6. 已审核术语能够约束 AI；
7. 系统能够发现至少一类需要确认的问题；
8. 用户能够在界面完成确认；
9. 系统完成基础 QA；
10. 系统生成英文 `.docx`；
11. 原文档主要格式和结构得到保留；
12. 重新启动软件后，已保存术语仍然存在；
13. 更换另一份说明书后仍可以运行；
14. 项目提供 README 和安装 / 启动说明。

满足以上条件即可认为 V1 核心闭环完成。

## P6：企业语言资产平台

**公司产品技术语言资产与 AI 翻译平台。**

# 18. 后续仍待讨论的问题

以下内容暂不在 V1 PRD 中强行确定，后续单独设计：

1. Candidate → Approved 的审核权限；
2. 公司级 / 产品线级 / 产品级术语继承；
3. 中英文历史说明书不完全一致时的 TM 对齐方式；
4. 候选术语自动识别方式；
5. 新术语确认机制；
6. QA Error / Warning / Info 分级；
7. Word 完整支持范围；
8. 图片翻译最终策略；
9. 语言资产版本管理与回滚；
10. 产品最终效果评估指标。

这些问题作为 V1 后续迭代和正式企业化的重要输入。
